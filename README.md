    Интерфейсы: Открытый (ограниченный доступ без ПКЗИ), Защищенный (полный, с ПКЗИ), Мобильный (согласование заявок).
    Аутентификация: Логин/пароль, ЭП, интеграция с AD/Entra ID.
    Функции пользователя: Заявки на доступ (для себя/других), отзыв, просмотр карточки (доступы, УЗ, трудоустройства, история), делегирование.
    Workflow заявок: Создание → Проверка SoD → Согласование (ЛинРук → ИБ компании → ИБ материнской → Владелец ИС/Роли) → Авто-исполнение/Ручное.
    Recertification: Ежеквартальный пересмотр доступов руководителем.
    Роли и доступы: RBAC, birthright-роли, SoD-конфликты, интеграция с 1С ЗУП для HR-данных.
    Отчеты: Статистика ролей, аудит входов, история изменений, SoD-проверки.
    Интеграции: 1С ЗУП (HR), Управляемые ИС (AD, LDAP, SCIM), уведомления (email/SIEM).

Из "инструкция администратора.docx":

    Администрирование: Привилегированные роли (Глобальный админ, Админ ИБ, Системный админ).
    Функции админа: Редактирование пользователей/ролей/ресурсов, настройка ИС, аудит, резервное копирование.
    Безопасность: Парольная политика, журналирование, контроль целостности, аудит событий, интеграция с SIEM.
    Режимы: Тестирование, Продуктив, Защита (аудит, ротация логов).
    Резервное копирование: Ежедневное, с RTO/RPO.
    Обновления: Проверки уязвимостей (MaxPatrol), установка патчей.

Система должна быть "в браузере" (web-based), с self-service, без бумажного документооборота, юридически значимым ЭДО.
Предлагаемый стек (100% open-source, проверенный на похожих проектах)

    IAM/IGA core: midPoint (роли, SoD, recertification, connectors к 1С/AD/SCIM).
    Auth/SSO: Authentik (OIDC/SAML/LDAP, красивый UI для self-service, mobile-friendly).
    Workflow engine: Temporal.io (сложные цепочки согласований с таймаутами, эскалациями, ежеквартальными кампаниями).
    Frontend: React.js (для всех интерфейсов: open/protected/mobile).
    Backend: Go (для custom логики: интеграции, отчеты; быстрый, безопасный).
    DB/Storage: PostgreSQL + MinIO (для данных и объектов).
    Deployment: Docker Compose (локально) → Kubernetes (k3s для demo масштаба).
    Security: Built-in в Authentik/midPoint (ЭП симуляция via JWT, аудит в ELK).
    Интеграции: midPoint connectors (1С via REST/CSV, AD/SCIM), Temporal для уведомлений (email/Slack для demo).
    Отчеты: midPoint reports + custom SQL в Go.

  * PostgreSQL: выполнены ли SQL-запросы?

  * Блокировка в Keycloak

  * Отключение MFA-устройств

    Дополнительно:

  * Блокировка IP-адреса источника (если известен)

  * Приостановка схожих учётных записей (по группе/подразделению)

    Удаление созданных злоумышленником объектов:

  * API-токены

  * Вебхуки

  * Новые учётные записи (если созданы)

    Смена паролей и MFA-токенов у пострадавшего пользователя
    Аудит всех систем, к которым был доступ

Проверка:

    Нет ли бэкдоров (например, скрытых правил перенаправления)
    Нет ли сохранённых сессий

    Возврат к нормальной работе:

    Постепенная выдача доступов (по принципу минимальных привилегий)
    Только после:

  * Подтверждения личности (MFA + звонок)

  * Обучения пользователя (phishing-awareness)

    Мониторинг активности в течение 7 дней (повышенная бдительность)

# sod_checker.py
SOD_RULES = {
    ("vendor_creator", "payment_approver"): "Нельзя создавать поставщика и утверждать платеж",
    ("developer", "production_deployer"): "Нельзя разрабатывать и деплоить в прод",
    ("inventory_clerk", "inventory_approver"): "Нельзя проводить и утверждать инвентаризацию",
}

def check_sod_conflict(user_roles: list, new_role: str) -> tuple[bool, str]:
    """
    Проверяет, создаёт ли добавление роли SoD-конфликт
    """
    for role in user_roles:
        if (role, new_role) in SOD_RULES or (new_role, role) in SOD_RULES:
            reason = SOD_RULES.get((role, new_role)) or SOD_RULES.get((new_role, role))
            return True, reason
    return False, ""

    # Получаем текущие роли (заглушка)
    current_roles = ["user"]  # в реальности — из FusionAuth

    # Проверка SoD
    conflict, reason = check_sod_conflict(current_roles, req.role)
    if conflict:
        log_event(req.user_id, "sod_violation", req.role, reason)
        raise HTTPException(403, detail=f"SoD conflict: {reason}")

    # Выдача роли
    log_event(req.user_id, "role_assigned", req.role)
    return {"status": "success", "role": req.role}

SOD_RULES = {
    ("vendor_creator", "payment_approver"): "Нельзя создавать поставщика и утверждать платеж",
    ("developer", "production_deployer"): "Нельзя разрабатывать и деплоить в прод",
}

def check_sod_conflict(user_roles: list, new_role: str) -> tuple[bool, str]:
    for role in user_roles:
        if (role, new_role) in SOD_RULES:
            return True, SOD_RULES[(role, new_role)]
        if (new_role, role) in SOD_RULES:
            return True, SOD_RULES[(new_role, role)]
    return False, ""

1. Общие сведения

Система управления правами доступа и учетными записями пользователей в корпоративных информационных системах (далее — ЦСУПД или IDM-система).

IDM-система предназначена для автоматизации процессов управления идентификацией, ролями, правами доступа и учетными записями пользователей в корпоративной среде компании с численностью более 1000 сотрудников. ### Описание проекта
Open-source платформа класса **Identity Governance & Administration** для крупных агропромышленных холдингов.  
Обеспечивает полный цикл управления идентификационными данными и доступом к 27 корпоративным системам в соответствии с лучшими практиками и требованиями регуляторов.

### Ключевые возможности

| Категория                  | Реализация                                                                 |
|----------------------------|-----------------------------------------------------------------------------|
| Пользователи               | 1000+ учётных записей, импорт из 1С ЗУП, автоматизация Joiner–Mover–Leaver |
| Роли и доступ              | 83 бизнес-роли, RBAC, 10 критических SoD-контролей                         |
| Workflow                   | 5-этапное согласование (линейный руководитель → ИБ → владелец ИС и др.)    |
| Ресертификация             | Ежеквартальные кампании с автоматическим отзывом просроченных доступов     |
| Self-service портал        | Desktop + Mobile PWA (React + Material-UI)                                 |
| Интеграции                 | 27 систем: SAP S/4HANA, 1С, Microsoft 365, ФГИС Зерно, ServiceNow и др.    |
| Compliance                 | SOX 404 · GDPR · 152-ФЗ · подготовлено к аудиту ФСТЭК                     |

# GreenAgroWise IGA/IDM · Central Access Management System (ЦСУПД)

**Enterprise Identity Governance & Administration Platform**  
Open-source IGA/IDM system for agribusiness holding with 1000+ employees

### Project Overview
Open-source **Identity Governance & Administration** platform designed for large-scale agribusiness enterprises.  
Provides full lifecycle management of identities and access to 27 corporate systems in compliance with industry best practices and regulatory requirements.

### Key Features

| Category               | Implementation                                                      |
|------------------------|---------------------------------------------------------------------|
| Users                  | 1000+ accounts, automated Joiner–Mover–Leaver processes             |
| Roles & Access         | 83 business roles, RBAC, 10 critical Segregation of Duties (SoD) rules|
| Workflow               | 5-stage approval process                                            |
| Recertification        | Quarterly access review campaigns with auto-revocation              |
| Self-Service Portal    | Desktop + Mobile PWA (React + Material-UI)                          |
| Integrations           | 27 systems: SAP S/4HANA, 1C, Microsoft 365, ФГИС Зерно, ServiceNow |
| Compliance             | SOX 404, GDPR, 152-FZ (Russia), FSTEC audit ready                   |
